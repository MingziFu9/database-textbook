# 9.1 事务

## 要么全做，要么全不做
| 语句 | 作用 |
|---|---|
| `START TRANSACTION;`（或 `BEGIN;`） | 开始一个事务 |
| `COMMIT;` | **提交**：永久保存所有修改 |
| `ROLLBACK;` | **回滚**：撤销所有修改 |

## 下单：三步放进一个事务
```sql
START TRANSACTION;
UPDATE product SET stock = stock - 2 WHERE product_id = 8;
INSERT INTO orders (customer_id, employee_id, order_time, pay_method, status)
VALUES (1, 3, '2026-07-01 08:15:00', '微信', '已完成');
INSERT INTO order_item (order_id, product_id, quantity, unit_price)
VALUES (LAST_INSERT_ID(), 8, 2, 26.90);
COMMIT;
```
- 燕麦片库存 91 → 89，订单 2502 和明细都在

::: notes
中途出错：写明细时商品编号写成不存在的 999，报 ERROR 1452 外键错误，执行 ROLLBACK 后薯片库存回到 8。要强调：MySQL 中事务里某条语句出错只是这一条失败，不会自动回滚整个事务，要由人或程序发出 ROLLBACK；第 11 章用 try…except 自动回滚。
:::

## 自动提交
| 操作 | 语句 |
|---|---|
| 查看是否自动提交 | `SELECT @@autocommit;`（1 开，0 关） |
| 本会话关闭 | `SET autocommit = 0;`，之后要手动 COMMIT |
| 临时用一次事务 | `START TRANSACTION; … COMMIT;` |

- MySQL 默认**每条语句自己就是一个事务**

## 事务的四个特性：ACID
| 特性 | 意思 | 小店的例子 |
|---|---|---|
| **原子性** | 要么全做，要么全不做 | 扣库存、写订单不会只做一半 |
| **一致性** | 前后都满足所有约束 | 库存不会变成负数 |
| **隔离性** | 同时进行，互不干扰 | 两边同时卖挂面不会都卖出 |
| **持久性** | 提交了就不会丢 | 服务器重启订单还在 |

# 9.2 并发与隔离级别

## 并发带来的三种问题
| 问题 | 发生了什么 |
|---|---|
| **脏读** | 读到别人**还没提交**、后来又撤销的修改 |
| **不可重复读** | 同一事务里**两次读同一行**，结果不同 |
| **幻读** | 同一事务里**两次按同样条件查**，行数不同 |

::: notes
脏读：A 把薯片从 8.90 改成 9.90 未提交，B 按 9.90 卖了，A 又撤销。不可重复读：B 对账先读到 8.90，A 改价并提交，B 再读变成 9.90。幻读：B 统计库存不足 10 件的商品，第一次 5 种，A 插入一种新商品后再查变成 6 种。
:::

## 四种隔离级别
| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| READ UNCOMMITTED | 会 | 会 | 会 |
| READ COMMITTED | 不会 | 会 | 会 |
| **REPEATABLE READ** | 不会 | 不会 | 会（标准） |
| SERIALIZABLE | 不会 | 不会 | 不会 |

::: notes
REPEATABLE READ 是 MySQL InnoDB 的默认值；READ COMMITTED 是 Oracle、PostgreSQL、SQL Server 的默认值。级别越高，并发问题越少，但等待越多。查看当前级别：SELECT @@transaction_isolation;
:::

## 编者实测：两个会话
| 场景 | B 的隔离级别 | A 做了什么 | B 读到 |
|---|---|---|---|
| ① | 读未提交 | 改价，未提交 | 9.90（脏读） |
| ② | 读已提交 | 改价，未提交 | 8.90 |
| ③ | 读已提交 | 改价并提交，B 再读 | 9.90（不可重复读） |
| ④ | 可重复读 | 同上 | 8.90 |

## 锁：一次只让一个人改
```sql
START TRANSACTION;
SELECT stock FROM product WHERE product_id = 5 FOR UPDATE;
-- 程序判断：stock >= 1 才继续，否则 ROLLBACK
UPDATE product SET stock = stock - 1 WHERE product_id = 5;
COMMIT;
```
- `FOR UPDATE`：读的同时**锁住这一行**，别人要等

::: notes
实验 9-2 场景⑤：A 修改燕麦片库存未提交，B 也来改，等 5 秒后报 ERROR 1205 Lock wait timeout exceeded（实验把等待时间设成 5 秒，默认 50 秒）。死锁：两个事务互相等对方的锁，InnoDB 会自动选一个回滚，报错 1213。避免办法：事务尽量短，按相同顺序访问数据。
:::

# 9.4 存储过程与存储函数

## 存储过程：起了名字的一组 SQL
```sql
DELIMITER //
CREATE PROCEDURE sp_low_stock(IN p_limit INT)
BEGIN
  SELECT product_id, name, stock FROM product
  WHERE stock < p_limit ORDER BY stock;
END //
DELIMITER ;

CALL sp_low_stock(10);
```

::: notes
DELIMITER 的作用：过程体里有分号，先把语句结束符临时换成 //，命令行才不会在第一个分号处就把语句送出去。DBeaver 里可以选中整个 CREATE PROCEDURE … END 按 Ctrl+Enter 执行。参数名习惯加 p_ 前缀。CALL sp_low_stock(10) 实测返回 5 行：挂面 0、橙汁 0、薯片 8、苹果 8、火锅底料 8。
:::

## 管理存储过程
| 操作 | 语句 |
|---|---|
| 查看有哪些 | `SHOW PROCEDURE STATUS WHERE Db = 'txshop';` |
| 查看定义 | `SHOW CREATE PROCEDURE sp_level;` |
| 删除 | `DROP PROCEDURE IF EXISTS sp_level;` |

- 参数有 **IN**（传入）、**OUT**（传出）、INOUT 三种

## 存储过程和存储函数
| | 存储过程 | 存储函数 |
|---|---|---|
| 调用 | `CALL 名字(…)` | 写在表达式里：`SELECT 名字(…)` |
| 返回 | 可以没有，或用 OUT 返回多个 | 必须 RETURN **一个值** |
| 适合 | 一组操作（汇总、批量更新） | 一个计算（算金额、算等级） |

## 什么时候用存储过程
| 适合 | 不太适合 |
|---|---|
| 固定的批处理，如每月汇总 | 复杂、常改的业务逻辑 |
| 多个程序共用的数据操作 | 要在不同数据库之间迁移的系统 |
| 减少程序和数据库的来回通信 | 调试、版本管理要求高的场合 |

# 9.5 触发器

## 自动执行的“开关”
- 绑在表上，INSERT、UPDATE、DELETE 时**自动执行**
- **BEFORE**：检查数据、拒绝不合格的修改
- **AFTER**：联动改别的表、记日志
- `FOR EACH ROW`：改 5 行就执行 5 次
- **NEW** 是新行，**OLD** 是旧行
  - INSERT 只有 NEW，DELETE 只有 OLD

## 卖出商品自动扣库存
```sql
CREATE TRIGGER trg_item_check BEFORE INSERT ON order_item
FOR EACH ROW
BEGIN
  IF (SELECT stock FROM product WHERE product_id = NEW.product_id)
     < NEW.quantity THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '库存不足，不能下单';
  END IF;
END //
CREATE TRIGGER trg_item_stock AFTER INSERT ON order_item
FOR EACH ROW
  UPDATE product SET stock = stock - NEW.quantity
  WHERE product_id = NEW.product_id //
```

::: notes
前后要加 DELIMITER // 和 DELIMITER ;。实测：买 3 包薯片成功，库存 8 → 5；买 1 包挂面（库存 0）报 ERROR 1644 (45000): 库存不足，不能下单。正文 9.5.3 还有改价日志触发器，用 OLD.price 和 NEW.price 记录改前改后的价格。
:::

## 触发器的风险
- **看不见**：看程序代码不知道它改了别的表
- **连锁反应**：触发器又触发别的触发器
- **拖慢速度**：批量导入时明显变慢
- 不能 COMMIT、ROLLBACK，不能改触发它的表
- 只做**简单、必须保证**的规则，写进设计文档

# 9.6 事件：定时执行的任务

## 每月 1 日自动汇总
```sql
CREATE EVENT ev_month_summary
ON SCHEDULE EVERY 1 MONTH STARTS '2026-08-01 02:00:00'
DO CALL sp_month_summary(
     DATE_FORMAT(CURDATE() - INTERVAL 1 MONTH, '%Y-%m'), @s);
```
- 事件调度器：`SHOW VARIABLES LIKE 'event_scheduler';`
- 查看 `SHOW EVENTS;`，删除 `DROP EVENT …;`

::: notes
二级 MySQL 大纲把触发器、事件、存储过程和存储函数并列为“数据库编程”的内容，四者都要会写简单的例子。
:::

## 前沿视窗：分布式事务与国产数据库
- 数据分布在很多台服务器上，怎样保证 ACID？
- 传统做法：**两阶段提交**，可靠但慢
- Google Spanner 用原子钟和 GPS 对时
- OceanBase、TiDB、PolarDB 支持分布式事务
