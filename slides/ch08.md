## 情景导入：100 万行订单，查一位顾客
| 查询 | 没有索引 | 有索引 |
|---|---|---|

# 8.1 视图

## 视图是“存起来的查询”
```sql
CREATE OR REPLACE VIEW v_order_detail AS
SELECT o.order_id, o.order_time, o.status,
       IFNULL(c.name, '散客') AS customer_name,
       p.name AS product_name, oi.quantity,
       oi.quantity * oi.unit_price AS subtotal
FROM orders o
LEFT JOIN customer c ON c.customer_id = o.customer_id
JOIN order_item oi   ON oi.order_id = o.order_id
JOIN product p       ON p.product_id = oi.product_id;
```
- 视图**不存数据**，查询时才去基本表取

## 管理视图
| 操作 | 语句 |
|---|---|
| 查看有哪些视图 | `SHOW FULL TABLES WHERE Table_type = 'VIEW';` |
| 查看定义 | `SHOW CREATE VIEW v_order_detail;` |
| 修改 | `CREATE OR REPLACE VIEW …` |
| 删除 | `DROP VIEW v_order_detail;` |

## 视图的三种用途
- **简化查询**：复杂连接藏起来，会计直接查视图
- **保护数据**：收银员只看价格和库存，不看进价
  - `v_cashier_product`：id、名称、售价、库存、单位
- **保持稳定**：表结构改了，改视图定义，报表不用改

## 哪些视图不能改
- 含聚合函数、DISTINCT、GROUP BY、HAVING
- 含 UNION、外连接
- 原因：一行由多行算出，**改不回基本表**
- `WITH CHECK OPTION`：改完的数据仍要满足视图条件
- **建议：视图主要用来查，改数据直接改基本表**

::: notes
试图修改分组视图会报 ERROR 1288 not updatable；在 v_drinks（category_id = 4，WITH CHECK OPTION）上把饮料改成别的类别，会报 ERROR 1369 CHECK OPTION failed。这两条错误都是实测的。
:::

# 8.2 索引是什么

## 书的目录
- 没有索引：一行一行翻，叫**全表扫描**
- 有索引：先查“目录”，直接翻到那几页
- 索引是按某列**排好序**的数据结构
- InnoDB 用 **B+ 树**

## 动手：在 B+ 树里找一个数
!sim bplus-tree
- 从根节点一层层往下找
- 三四层就能管上千万行
- 叶子节点连成链，**范围查询**顺着走

## 聚簇索引和二级索引
| | 聚簇索引 | 二级索引 |
|---|---|---|
| 是谁 | 一般就是主键 | 自己建的其他索引 |
| 叶子存什么 | **整行数据** | 索引列的值 + 主键 |
| 查法 | 一步到位 | 找到主键再**回表** |
| 比方 | 按学号排的档案柜 | 姓名 → 学号对照表 |

::: notes
两条结论：每张表都要有主键，最好是短小的自增整数；查询要的列全在二级索引里就不用回表，叫覆盖索引，EXPLAIN 的 Extra 显示 Using index。这也是不要 SELECT * 的原因之一。
:::

# 8.3 创建和管理索引

## 四种常用索引
| 索引 | 怎么来 | 特点 |
|---|---|---|
| 主键索引 | PRIMARY KEY 自动建 | 就是聚簇索引 |
| 唯一索引 | UNIQUE 或 `CREATE UNIQUE INDEX` | 值不能重复 |
| 普通索引 | `CREATE INDEX` | 只为查得快 |
| 组合索引 | `CREATE INDEX … (列1, 列2)` | 先按列1排，再按列2 |

## 建索引的语句
```sql
CREATE INDEX idx_customer ON orders_big (customer_id);
CREATE UNIQUE INDEX uk_phone ON customer (phone);
CREATE INDEX idx_cust_time ON orders_big (customer_id, order_time);

SHOW INDEX FROM orders_big;
DROP INDEX idx_customer ON orders_big;
```

## 组合索引与最左前缀
- 索引 (customer_id, order_time) 像电话簿：**先姓后名**
- 查 customer_id：用得上
- 查 customer_id 和 order_time：用得上
- 只查 order_time：**用不上**
- 区分度高、最常用的列放前面

## 什么列该建，什么列不该
| 该建 | 不该建 |
|---|---|
| 常在 WHERE 里筛选的列 | 很少用来查询的列 |
| 常用来连接的列（外键） | 值的种类很少的列（性别、状态） |
| 常用来排序、分组的列 | 只有几百行的小表 |
| 要求唯一的列 | 经常大批量修改的列 |

## 索引的代价（实验 8-2 实测）
- **占空间**：100 万行数据 142.8 MB，3 个索引又占 60.6 MB
- **拖慢写入**：插入 20 万行，1.01 秒 → 3.22 秒
- **建索引要时间**：100 万行约 1 秒
- 原则：为**真正常用**的查询建索引

# 8.4 看懂执行计划：EXPLAIN

## 在查询前加 EXPLAIN
| | type | key | rows |
|---|---|---|---|
| 没有索引 | **ALL** | NULL | 1342536 |
| 有 idx_customer | **ref** | idx_customer | 50 |

- `EXPLAIN SELECT * FROM orders_big WHERE customer_id = 12345;`
- 只显示计划，**不真正执行**

## 先会看三列
| 列 | 意思 | 怎么看 |
|---|---|---|
| **type** | 访问方式 | 最怕 ALL；range、ref、const 都好 |
| **key** | 实际用的索引 | NULL 表示没用上 |
| **rows** | 预计检查的行数 | 越小越好，是估计值 |

## type 从好到差
| type | 意思 | 例子 |
|---|---|---|
| const | 按主键找一行 | `WHERE order_id = 2499` |
| eq_ref | 连接时按主键找一行 | 明细连商品表 |
| ref | 按普通索引找若干行 | `WHERE customer_id = 12345` |
| range | 按索引找一个范围 | `order_time >= … AND < …` |
| index | 整个索引扫一遍 | 对索引列用了函数 |
| ALL | 全表扫描 | 没有可用的索引 |

# 8.5 让索引失效的常见写法

## 五种“索引白建”（实验 8-3 实测）
| 慢的写法 | 改写 | 实测 |
|---|---|---|
| `DATE(order_time) = '2026-06-30'` | `order_time >= … AND < …` | index → range |
| `phone = 10005864824` | `phone = '10005864824'` | ALL → ref |
| `phone LIKE '%64824'` | `LIKE '1000586%'` | ALL → range |
| `… OR amount > 304.9` | 给 amount 也建索引 | ALL → index_merge |
| 组合索引上只查 order_time | 带上第一列 | ALL → range |

::: notes
共同的原因：索引里存的是列的原值，按顺序排好。对列用函数、隐式类型转换、以 % 开头的模糊匹配，都让数据库没法按顺序去找。phone 是 CHAR(11)，和数字比较时每一行都要先转换类型，等于对列用了函数。耗时：0.25 秒 → 0.00 秒，0.16 秒 → 0.00 秒，0.48 秒 → 0.02 秒，0.51 秒 → 0.00 秒。
:::

## 一句话记住
- WHERE 里的**索引列保持干净**
- 不对它用函数、不做运算
- 类型要对上：字符串加引号
- 模糊查询不以 % 开头
- 组合索引从**最左列**开始用

# 8.6 查询优化的实用习惯

## 六条习惯
- 只取需要的列，少用 `SELECT *`
- 用 **LIMIT** 限制行数
- WHERE 里的索引列保持干净
- 能在 WHERE 里筛的不放 HAVING
- 连接的列要有索引
- **先 EXPLAIN 再上线**

## 慢查询日志：找到慢 SQL
```sql
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.1;   -- 超过 0.1 秒就记下来
SHOW VARIABLES LIKE 'slow_query_log_file';
```
- 日志里：`Query_time: 0.304686  Rows_examined: 1000000`

::: notes
日志里 Rows_examined 100 万、只返回 1 行，一看就是没用上索引。long_query_time 默认是 10 秒；实验结束后记得关掉慢查询日志，把 long_query_time 设回 10。正文的视图还多了付款方式和类别两列，这里为了一页放下做了精简。
:::
