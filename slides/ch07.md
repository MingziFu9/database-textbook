# 7.1 数据冗余与三种异常

## 三种异常
| 异常 | 意思 |
|---|---|
| **更新异常** | 同一信息存多处，漏改一处就矛盾 |
| **删除异常** | 删数据时把别的信息也删了 |
| **插入异常** | 缺少别的信息，放不进去 |

::: notes
例子：顾客换号，几十行只改了一行；删掉唯一一张买过生抽的订单，“生抽属于调味品”也没了；新商品没人买过，没有订单号，放不进大表。
:::

# 7.2 函数依赖

## “知道了 A，就能确定 B”
| 函数依赖 | 业务含义 |
|---|---|
| order_id → order_time, customer_id | 一张订单一个时间、一位顾客 |
| customer_id → customer_name, phone | 一位顾客一个姓名、一个电话 |
| product_id → product_name, category | 一种商品一个名称、一个类别 |
| (order_id, product_id) → quantity | 成交数量由两者共同确定 |

## 三种依赖
- **完全依赖**：要整个码才能确定
- **部分依赖**：只要码的**一部分**就能确定
  - product_id → product_name
- **传递依赖**：码 → A → B
  - order_id → customer_id → customer_name

# 7.3 第一、第二、第三范式

## 动手：从大表到第三范式
!sim normal-forms
- 第 0 步：数一数电话存了几遍
- 找部分依赖，拆到 2NF
- 找传递依赖，拆到 3NF

## 1NF：一格一值
| order_id | customer | 商品 |
|---|---|---|
| 46 | 郑伟涛 | 鲜肉包×3，海苔×1，生菜×2 |

- 一格放了多个值，**不满足 1NF**
- 拆成多行，每行一种商品

## 2NF：不能只靠码的一部分
| 非主属性 | 依赖于 | 部分依赖？ |
|---|---|---|
| order_time、customer_… | 只要 order_id | 是 |
| product_name、category_name | 只要 product_id | 是 |
| unit_price、quantity | 整个码 | 否 |

- 把部分依赖的列**连同决定因素**拿出去

## 3NF：只看码，不看别人
!mermaid 1
- 订单表里：order_id → customer_id → customer_name
- 把顾客信息拆成**顾客表**
- 订单表只留 customer_id 作外键

## 拆得开、拼得回
- 拆分后用**连接**拼回原表
- 行数应和原表一样（实验 7-2：174 行）
- 拆出的表：顾客 82 行、订单 45 行、商品 13 行

# 7.4 BC 范式与答题步骤

## 范式一览
| 范式 | 口诀 | 违反时怎么拆 |
|---|---|---|
| 1NF | 一格一值 | 多值拆成多行 |
| 2NF | 不能只靠码的一部分 | 部分依赖拿出去 |
| 3NF | 只看码，不看别人 | 传递依赖拿出去 |
| BCNF | 能决定别人的都是码 | 违反的依赖单独成表 |

## 范式判断题的答题步骤
- ① 写出**函数依赖**
- ② 找出**码**（候选键）
- ③ 有部分依赖？→ 只到 1NF
- ④ 有传递依赖？→ 只到 2NF
- ⑤ 都没有 → 3NF；写出拆分结果

# 7.6 反规范化

## 故意保留一些冗余
| 做法 | 好处 | 代价 |
|---|---|---|
| 会员表存当前积分 | 查余额不用求和 | 两处要同步改 |
| 订单表存总金额 | 统计不用连接明细 | 改明细要改总额 |
| 每晚生成日汇总表 | 报表秒开 | 有一天延迟 |

::: notes
反规范化要写清理由，并用事务、触发器或定期核对保证一致。实验里演示了存的总金额 152.60 与明细算出的 132.70 不一致的例子。订单明细里存“成交单价”也是有意保留的冗余：商品会调价，历史订单要按当时的价格算。
:::

## 前沿视窗：大数据时代的“宽表”
- 数据仓库常把很多表拼成一张**宽表**
- 只读不改，冗余换查询速度
- 业务库仍按范式设计
- 不同场景，不同取舍

## 本章小结
- 冗余带来更新、删除、插入三种异常
- 部分依赖违反 2NF，传递依赖违反 3NF
- 拆分：把依赖的列连同决定因素拿出去
- 一般设计到 3NF；反规范化要写清理由
